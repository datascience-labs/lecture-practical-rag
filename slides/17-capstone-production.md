## 오늘의 목표

## 전체 커리큘럼 되돌아보기

```
기초 (1~5회차)                검색 고도화 (6~9회차)
├─ RAG 개념                  ├─ 하이브리드 검색 (BM25+RRF)
├─ 임베딩                    ├─ 리랭킹 (cross-encoder)
├─ 벡터 DB (ChromaDB)        ├─ 쿼리 변환 (rewrite/multi-query/HyDE)
├─ 청킹 전략                 └─ 평가 (Hit@k, MRR, RAGAS)
└─ 기본 파이프라인
                             그래프 RAG (10~14회차)
                             ├─ 지식 그래프 기초
                             ├─ GraphRAG (커뮤니티 요약, 전역 질문)
                             ├─ OntoRAG (온톨로지 제약, 추론)
                             └─ NodeRAG (이종 노드, PPR)

멀티모달 (15~16회차)
├─ 오픈소스 VLM (Qwen2.5-VL, Ollama)
├─ CLIP 이미지 검색 / ColPali 도면·문서 검색
└─ 현장 사진 구조화 분석 → RAG 환류
```

## 아키텍처 결정 트리

```
시작: 항상 기본 RAG(5회차)부터. 평가셋(9회차)을 먼저 만든다.
│
├─ 키워드/코드명 검색 실패가 많다 → 하이브리드 검색 (6)
├─ 정답이 후보엔 있는데 순위가 낮다 → 리랭킹 (7)
├─ 멀티턴 대화 서비스다 → 쿼리 재작성 (8) [사실상 필수]
├─ 재현율이 낮다 → Multi-Query / HyDE (8) [평가로 검증]
│
├─ multi-hop·관계 질문이 실패한다
│   ├─ 관계에 명확한 규칙·계층이 있다 → OntoRAG 제약 (13)
│   └─ 세부 사실의 정밀 검색이 관건 → NodeRAG 구조 (14)
│
├─ 전역·요약 질문이 필요하다 → GraphRAG 커뮤니티 요약 (11~12)
│
├─ 도면·사진 등 비텍스트 자료가 핵심이다
│   ├─ 문서/도면 페이지 검색 → ColPali 계열 (16)
│   └─ 사진 내용 검색·분석 → VLM 캡셔닝/구조화 + CLIP (15~16)
│
└─ 각 단계마다: 평가 지표가 개선됐는가? 지연·비용은 감당 가능한가?
```

**철칙**: 복잡한 기법은 **측정된 실패**가 근거일 때만 추가한다

## 프로덕션 요소 1: 인덱싱 운영

- **증분 인덱싱**: 문서 변경 감지(해시) → 해당 청크만 재처리
- **버전 관리**: 인덱스 버전 태깅 → 문제 시 롤백
- **동기화 파이프라인**: 원본 저장소(위키, 드라이브) → 주기적/이벤트 기반 갱신
- 그래프 RAG의 경우: 추출 결과 캐시 필수 (12회차), 커뮤니티 재계산 주기 결정

```
문서 저장소 ──변경 감지──▶ 청킹·추출 워커 ──▶ 벡터DB/그래프 (스테이징)
                                                  │ 평가셋 자동 검증 통과 시
                                                  ▼
                                              프로덕션 스왑
```

---

## 프로덕션 요소 2: 서빙 최적화

**프롬프트 캐싱** — 시스템 프롬프트와 고정 문서를 캐시해 비용·지연 절감:

```python
response = client.messages.create(
    model="claude-opus-4-8",
    max_tokens=2048,
    system=[{
        "type": "text",
        "text": LONG_SYSTEM_PROMPT,          # 고정 부분
        "cache_control": {"type": "ephemeral"},   # ← 캐시 지점
    }],
    messages=[{"role": "user", "content": prompt}],  # 가변 부분은 뒤에
)
# response.usage.cache_read_input_tokens 로 캐시 적중 확인
```

- **시맨틱 캐시**: 유사 질문의 답변 재사용 (질문 임베딩 유사도 기반)
- **모델 라우팅**: 단순 질문 → Haiku, 복잡 질문 → Opus (8회차 분류기 응용)
- **배치 API**: 실시간이 아닌 대량 처리(평가, 인덱싱)는 Batches API로 50% 절감

## 프로덕션 요소 3: 안전과 보안

| 위협 | 대응 |
|---|---|
| 프롬프트 인젝션 (문서에 악성 지시문) | 문서를 데이터로 취급하는 프롬프트 구조, 출력 검증 |
| 권한 밖 문서 노출 | 검색 단계 메타데이터 필터로 ACL 강제 (3회차) — **생성 후 필터링은 늦다** |
| PII 유출 | 인덱싱 시 마스킹, 답변 후처리 검사 |
| 환각으로 인한 오정보 | 출처 표기 강제, 충실성 임계값(9회차) 미달 시 답변 보류 |

```python
# 권한 필터는 반드시 검색 쿼리에서
collection.query(query_texts=[q],
                 where={"allowed_groups": {"$in": user.groups}})
```

## 프로덕션 요소 4: 모니터링

**오프라인 평가** (배포 전, 9회차):

- 평가셋 자동 실행 → Hit@k, faithfulness 회귀 감지

**온라인 모니터링** (배포 후):

- 사용자 피드백 (👍/👎) 수집 → 실패 사례가 평가셋으로 환류
- 검색 거리/리랭크 점수 분포 — "관련 문서 없음" 비율 추적
- 지연시간 백분위(p50/p95), 토큰 비용 대시보드
- **환류 루프**: 나쁜 피드백 → 원인 분류(검색/생성) → 평가셋 추가 → 개선 → 재배포

## 종합 프로젝트 요구사항

본인 도메인 코퍼스로 다음을 포함한 RAG 시스템 완성:

**필수**

1. 인덱싱 파이프라인 (로딩→청킹→임베딩→저장, 재실행 가능)
2. 하이브리드 검색 + 리랭킹
3. 평가셋 20문항 이상 + 자동 평가 하네스 + 개선 이력표
4. 출처 표기와 "모름" 처리

**선택 (1개 이상)**

5. GraphRAG / OntoRAG / NodeRAG 중 택1 적용 — **도입 근거를 평가 데이터로 제시**
6. 멀티모달: 도면/사진/문서 이미지 검색 또는 VLM 분석 파이프라인 (15~16회차)
7. 멀티턴 대화 (쿼리 재작성)
8. 프로덕션 요소 1가지 (캐싱, 권한 필터, 모니터링 등)

---

## 발표 형식 (팀당 10분)

1. **문제 정의** (1분): 어떤 문서, 어떤 사용자, 어떤 질문?
2. **아키텍처** (2분): 결정 트리에서 무엇을 선택했고 왜?
3. **평가 결과** (3분): 단계별 개선 지표 — 표로!
4. **실패 사례 분석** (2분): 여전히 안 되는 것과 원인 진단
5. **데모** (2분): 라이브 질의응답

평가 기준: 지표 기반 의사결정 (40%) / 완성도 (30%) / 실패 분석의 깊이 (30%)

> "무엇을 썼는가"보다 "**왜 그것을 선택했는가**"가 핵심

## 더 공부할 주제들

- **Agentic RAG**: LLM이 검색 도구를 스스로 호출·반복하는 에이전트 루프 (tool use)
- **VLM 파인튜닝**: LoRA로 도메인 도면 심볼·현장 사진에 특화 (16회차 정확도 한계 돌파)
- **LightRAG / HippoRAG**: 그래프 RAG의 경량·신경과학 영감 변형들
- **Long-context vs RAG**: 1M 토큰 시대의 역할 분담 — 그래도 RAG가 필요한 이유 (비용, 최신성, 권한)
- **파인튜닝 결합**: 임베딩 모델 도메인 파인튜닝, 검색 증강 파인튜닝(RAFT)
